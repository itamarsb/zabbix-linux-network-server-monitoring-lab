# Stage 08 - SNMP Network Monitoring and Optional Grafana Integration

## Objective

This stage introduces SNMP-based monitoring for a controlled network-oriented target.

The implementation will first establish a complete native Zabbix SNMP workflow. Grafana will be considered only after SNMP collection, visualization, failure detection, recovery, and troubleshooting have been validated directly in Zabbix.

The stage will cover:

- SNMP fundamentals used in network operations;
- deployment of a controlled SNMP-enabled target;
- UDP port `161` connectivity;
- SNMP version and community configuration;
- direct command-line polling;
- Zabbix host registration with an SNMP interface;
- standard system OIDs;
- interface discovery and monitoring;
- item-value interpretation;
- native Zabbix graphs;
- trigger configuration;
- controlled SNMP failure simulation;
- problem detection and recovery;
- notification behavior;
- SNMP troubleshooting;
- selected technical evidence;
- optional Grafana integration.

## Implementation Principle

Native Zabbix monitoring will be completed before any optional Grafana integration.

This sequence ensures that:

- SNMP connectivity is validated independently;
- collected values are understood before visualization;
- monitoring failures are not confused with dashboard failures;
- triggers and incidents remain managed by Zabbix;
- Grafana, if introduced, acts only as an additional visualization layer.

## SNMP Concepts

### Manager

The SNMP manager requests information from monitored devices.

In this laboratory, Zabbix Server performs the manager role.

### Agent

The SNMP agent exposes management information about a monitored device or service.

The controlled SNMP target will perform the agent role.

### Object Identifier

An Object Identifier, or OID, uniquely identifies a managed value.

Examples include:

- system description;
- system name;
- system uptime;
- interface name;
- interface administrative status;
- interface operational status;
- received octets;
- transmitted octets.

### Management Information Base

A Management Information Base, or MIB, describes the structure and meaning of SNMP objects.

Numeric OIDs will be validated first to reduce dependency on locally installed MIB files.

### Community

An SNMP community acts as a shared access value in SNMPv2c.

The laboratory community value will be environment-specific and must not be committed directly to the repository.

## Protocol Selection

The initial implementation will use SNMPv2c.

| Setting | Planned value |
|:---:|---|
| Protocol | SNMP |
| Version | SNMPv2c |
| Transport | UDP |
| Agent port | `161` |
| Access mode | Read only |
| Community storage | Local environment variable |
| Public exposure | Not allowed |
| Monitoring source | Zabbix Server container |

SNMPv2c is appropriate for this isolated introductory laboratory because it allows direct examination of OIDs, values, polling behavior, and connectivity.

SNMPv3 remains the recommended choice for production environments that require authentication and encryption.

## Security Scope

The SNMP implementation must follow these controls:

- the target is limited to the controlled laboratory;
- SNMP access is read only;
- the community value is not embedded in tracked files;
- UDP `161` is not exposed publicly;
- the SNMP target is attached only to the required Docker network;
- no production network device is queried;
- no router, switch, access point, or ISP-managed device is modified;
- no personal credential is committed;
- diagnostic output is reviewed before publication.

## Planned Monitoring Signals

The initial SNMP validation will prioritize standard OIDs.

| Monitoring signal | Purpose |
|---|---|
| System description | Identifies the monitored SNMP implementation |
| System object identifier | Identifies the agent or device class |
| System uptime | Confirms continued target operation |
| System name | Confirms target identity |
| Interface description | Identifies discovered interfaces |
| Interface administrative status | Shows the configured interface state |
| Interface operational status | Shows the effective interface state |
| Received octets | Provides inbound traffic data |
| Transmitted octets | Provides outbound traffic data |

Additional values will be introduced only when they produce meaningful operational evidence.

## Controlled Failure Plan

The failure test will interrupt only the SNMP monitoring target.

The PostgreSQL database, Zabbix Server, Zabbix Web, Mailpit, monitored HTTP service, Windows Agent 2, Linux Agent 2, and unrelated monitored hosts must remain available.

Expected failure behavior:

| Signal | Normal state | Failure state | Recovery state |
|---|:---:|:---:|:---:|
| SNMP target container | Healthy | Stopped or unavailable | Healthy |
| SNMP polling | Successful | Unavailable | Successful |
| SNMP availability | Available | Unavailable | Available |
| SNMP problem event | Absent | Present | Resolved |
| Notification lifecycle | No new message | Problem message | Recovery message |

The final trigger behavior will be defined only after the normal polling interval and availability characteristics have been observed.

## Grafana Decision Gate

Grafana integration is optional.

It will be considered only if all of the following conditions are met:

- the SNMP target is stable;
- direct polling succeeds;
- Zabbix receives current values;
- interface discovery succeeds;
- native Zabbix graphs are available;
- controlled failure detection succeeds;
- service recovery succeeds;
- the incident lifecycle is preserved;
- the optional integration adds portfolio value without duplicating another repository unnecessarily.

If these criteria are not met, the stage will be completed with native Zabbix SNMP monitoring only.
